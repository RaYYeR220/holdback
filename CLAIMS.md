# Claims

Every public statement about Holdback, with the file or script behind it. Four tags:

- **REPRODUCIBLE**: anyone can check it without credentials, with `pnpm -r test` or a file in this repo.
- **VERIFIED-LIVE**: it happened in a real run, with the real Kane CLI, Claude Code and the Venice API, and a recorded ledger or live capture in this repo shows it.
- **MODELED**: derived or rendered from recorded data; not observed as such.
- **NOT-CLAIMED**: what Holdback does not do, or has not shown yet.

## What the demo run showed

The pantry run also showed three things about Holdback itself.

- **Seen:** the guard matched `.holdback` and `.testmuai` anywhere in lowercased text, so a Write of app code that read `process.env.HOLDBACK_TODAY` was denied, although the spec's `STACK.md` asks the app to read `HOLDBACK_TODAY` and `HOLDBACK_NOW`. The code of turn 1 left that requirement as a TODO naming the guard. In turn 4 the agent's code read the variable through a name built at run time, `['HOLD', 'BACK_'].join('') + 'TODAY'`, which the guard did not match.
- **What it means:** the guard is a string matcher. It denied a read the spec asks for, and a string built at run time got past it. A read of the verifier through a path built the same way would get past it too ([Not claimed](#not-claimed)).
- **Holdback now:** the guard's folder names, Holdback's own paths and the git internals match wherever they occur, unless a letter, digit or `_` follows them. `process.env.HOLDBACK_TODAY`, `env.holdback_now` and `obj.testmuai_id` are allowed; `~/.holdback/x`, `C:\Users\u\.holdback\v`, `cat .testmuai/tests/a.md`, `"$HOME/.holdback"`, `$D.holdback/v/a.md` and `-C.holdback` are still denied (`packages/core/src/agent/guard.ts`; `packages/core/test/guard.test.ts`).

The same run stalled before the gate opened, and that is the second thing it showed:

- **Seen:** after turn 4 the run stood at 20 of 57 criteria green, 23 owed and 8 tests whose Kane runs proved nothing (timeouts, Kane's own fixture trouble). Every owed criterion carried such a test, and two of them also carried a report of Kane's against the app; one of those, that the volunteer list cannot be reached, was wrong: the page's `<a href="/volunteer">` link works. The gate never opened, so no planted bug was ever tried on the 20 passing criteria. For two turns the agent changed no file, and Kane checked the same code again each turn.
- **What it means:** a gate that cannot open for reasons more turns will not fix kept the run from proving anything, and turns that changed nothing cost turns and Kane credits on code nobody changed.
- **Holdback now:** two agent turns in a row that end normally and change nothing on code Kane checked with the app up stall the build loop, whatever is owed (`build.stalled`, R48). The stop lists Kane's reports on the app the agent did not act on (disputed: review them) and Kane's own runs that proved nothing. Kane does not check unchanged code again (only a test whose last run proved nothing runs once more). On a stall, or when only Kane's inconclusive runs keep the gate shut, `holdback run` falsifies the passing criteria all the same and stops held back (exit 3); the verdict says what it falsified ([below](#what-the-code-does)). The turn limit does the same (exit 1), and `--max-turns 0` falsifies what Kane last saw pass without another turn or check: that is how this run's planted-bug pass ran, on 26 passing criteria.

The planted-bug pass showed the third thing:

- **Seen:** all 6 planted bugs that got past their criterion's tests broke nothing that criterion says: 3 patches change no behaviour and 3 change a different rule ([the pantry run](#the-pantry-run)). Holdback recorded them as survivors, made 4 criteria vacuous and had Kane evolve two use cases on the breaker's account of a bug that was not there. uc-3's evolve cost 13 criteria their test.
- **What it means:** a survivor is only as good as the breaker's patch. Holdback checks that a patch applies and the app starts, not that it changes what the criterion says; Kane's tests were right about all 6.
- **Holdback now:** a patch that changes no code is set aside before any replay (m-ac-53-1's would be), and a bug Kane's replay lets through counts only when the referee, a second model call, names an input where it visibly breaks its criterion; else it is invalid and the criterion keeps its status. The referee's prompt, tried live on m-ac-53-1, rejected it ("no-change"), and confirmed the rehearsal's real survivor ([below](#what-the-code-does)). The referee is an LLM's judgment, not a proof ([Not claimed](#not-claimed)).

## Not claimed

- **OS-level isolation of the verifier.** It is a seal, a guard hook, deny rules and hashes, not a sandbox. The threat model is an agent that optimizes toward green, not one that attacks Holdback.
- **Distrust of Kane's own verifier state.** Holdback trusts Kane's own verifier state; it is outside the agent's reach and hash-checked before every Kane step. After an evolve, Holdback seals only Kane's new test files of the use case and the tests it retired there, and refuses (as a tamper) any other change, a graph that names a test or file twice, or a new test that verifies another use case's criteria; it does not otherwise second-guess what Kane's store says.
- **A guard that stops obfuscated shell.** It is best-effort: a string matcher. For example, `git -c` keys on an allowed read-only subcommand (a diff driver, a pager) can still run a command, and a command name assembled at run time (`$(echo hold)back reseal`) gets past the check for the human's Holdback commands. A re-seal is logged in the ledger either way.
- **Keeping the agent from reading the hidden tests.** The deny rules and the guard stop the reads they recognise. A shell read through a path assembled at run time is not prevented: the demo run's code built `HOLD` + `BACK_` at run time, and that read a name the guard denies ([above](#what-the-demo-run-showed)), and a path to the verifier can be built the same way, so the agent could read the hidden tests. Nothing in Holdback would notice such a read.
- **Preventing a change.** The seal's hashes detect a change to a sealed file (a test, a variable, the spec, the config, Kane's recordings) after the fact: the next check records it as a tamper and the gate stays shut until a human re-seals. They do not stop a read, and they do not stop a write; they make one visible.
- **A sealed window while Kane runs.** The app the agent wrote runs as your user while Kane tests it, so in that window it could change files Holdback seals. That window is outside the threat model.
- **A view the agent cannot change.** `status` and `owed` decide what to show by reading the `CLAUDECODE` variable. An agent with shell access can unset it and see the human view, which can name Holdback's folders and Kane's test files, and says which Kane runs proved nothing and why. Neither view prints what Kane was told after a surviving bug, nor Kane's question when it disputes one or the referee's reason when it rejects one (`status` names only the criterion and the bug), but that text is on Kane's command line while the evolve runs, in Kane's own store in the verifier and in the ledger in Holdback's home, so an agent process that is running then, or a shell read the guard misses, could still find it.
- **Telling who changed the spec.** Holdback knows only when it saw a change, not who made it, so it never takes one for yours once an agent turn has run since the latest drift you approved interactively (or since the first seal, if there has been none). Before any turn, a change counts as yours: an agent process left running from an earlier session could still have made it. A shell write the guard does not recognise (a script, an assembled command) is not on record as an attempt, so the change reads as drift of unverified origin rather than a tamper. Logging an attempt is best effort: one that cannot be written is still denied, but not on record.
- **Instant notice of Bash edits to git-ignored files.** In interactive mode they are not noticed until the next Edit or Write.
- **Privacy from Kane CLI's cloud.** Kane uploads test runs, screenshots and the pages it saw to LambdaTest Test Manager (`upload.performed: true` in every captured run under `packages/core/test/fixtures/kane/`). Holdback passes no option to change that.
- **Redacted Kane evidence.** Kane's evidence packs in the verifier folder stay as Kane writes them. Only the public fixture drops them (`apps/dashboard/scripts/sanitize-ledger.mjs`).
- **Low Kane cost.** In the first live run, authoring cost about 16 credits per test step, and a test that keeps failing is authored again on every run. Confirming a catch with a second replay adds Kane's verdict on it, about 3 credits. The pantry run spent 5,233.9 Kane credits; Claude Code with its own Kane checks spent 65 on the same spec.
- **A referee that is right.** The referee is an LLM's judgment from the criterion, its spec quotes and the patch, not a proof, and its words are not checked against the code (its reason for m-ac-53-1 named a change the patch does not make). Equivalent mutants it misjudges are not claimed away: a patch whose effect is undone or never read outside the lines it is shown (m-ac-36-1's `eligible: false`, overridden by the object's own key further down) can still be confirmed and sent to Kane. It can also reject a real survivor, which then proves nothing. The no-op filter catches only unchanged lines or tokens, not an expression swapped for an equal one (m-ac-20-1). In the pantry run, before both existed, all 6 survivors were such patches ([above](#what-the-demo-run-showed)); the referee has been tried live on two patches, not in a pass.
- **A referee independent of the breaker.** The referee and the breaker are the same model (`breaker.model`), so their errors can correlate: a misreading of the code that produced the patch can also confirm it.
- **A referee the patch cannot steer.** The patch is text the breaker (or anyone who can shape the code it is shown) wrote, and the referee reads it whole, so a patch's text can steer what the referee says, including the input and results Kane is then told.
