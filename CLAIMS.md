# Claims

Every public statement about Holdback, with the file or script behind it. Four tags:

- **REPRODUCIBLE**: anyone can check it without credentials, with `pnpm -r test` or a file in this repo.
- **VERIFIED-LIVE**: it happened in a real run, with the real Kane CLI, Claude Code and the Venice API, and a recorded ledger or live capture in this repo shows it.
- **MODELED**: derived or rendered from recorded data; not observed as such.
- **NOT-CLAIMED**: what Holdback does not do, or has not shown yet.

## Not claimed

- **OS-level isolation of the verifier.** It is a seal, a guard hook, deny rules and hashes, not a sandbox. The threat model is an agent that optimizes toward green, not one that attacks Holdback.
- **Distrust of Kane's own verifier state.** Holdback trusts Kane's own verifier state; it is outside the agent's reach and hash-checked before every Kane step. After an evolve, Holdback seals only Kane's new test files of the use case and the tests it retired there, and refuses (as a tamper) any other change, a graph that names a test or file twice, or a new test that verifies another use case's criteria; it does not otherwise second-guess what Kane's store says.
- **A guard that stops obfuscated shell.** It is best-effort. For example, `git -c` keys on an allowed read-only subcommand (a diff driver, a pager) can still run a command, and a command name assembled at run time (`$(echo hold)back reseal`) gets past the check for the human's Holdback commands. A re-seal is logged in the ledger either way.
- **A view the agent cannot change.** `status` and `owed` decide what to show by reading the `CLAUDECODE` variable. An agent with shell access can unset it and see the human view, which can name Holdback's folders and Kane's test files, and says which Kane runs proved nothing and why. Neither view prints what Kane was told after a surviving bug, but that text is on Kane's command line while the evolve runs and in the ledger in Holdback's home, so an agent process that is running then, or a shell read the guard misses, could still find it.
- **Telling who changed the spec.** Holdback knows only when it saw a change, not who made it, so it never takes one for yours once an agent turn has run since the seal. Before any turn, a change counts as yours: an agent process left running from an earlier session could still have made it. A shell write the guard does not recognise (a script, an assembled command) is not on record as an attempt, so the change reads as drift of unverified origin rather than a tamper. Logging an attempt is best effort: one that cannot be written is still denied, but not on record.
- **Instant notice of Bash edits to git-ignored files.** In interactive mode they are not noticed until the next Edit or Write.
- **A sealed window while Kane runs.** The app the agent wrote runs as your user while Kane tests it, so in that window it could change files Holdback seals. That window is outside the threat model.
- **Privacy from Kane CLI's cloud.** Kane uploads test runs, screenshots and the pages it saw to LambdaTest Test Manager (`upload.performed: true` in every captured run under `packages/core/test/fixtures/kane/`). Holdback passes no option to change that.
- **Redacted Kane evidence.** Kane's evidence packs in the verifier folder stay as Kane writes them. Only the public fixture drops them (`apps/dashboard/scripts/sanitize-ledger.mjs`).
- **Low Kane cost.** In the first live run, authoring cost about 16 credits per test step, and a test that keeps failing is authored again on every run.
- **The planted-bug pass started by `holdback run`.** In the first live run the gate never opened. The pass ran the same `runFalsify` code from a script while the gate was shut, with real Kane and the real breaker.
- **The full loop live.** A Kane bug report reaching the agent and the agent fixing it, spec edits reopening work, Kane's evolve of a use case inside `holdback run` and the re-check of the bug that got through (the evolve itself ran live on a copy of the verifier, above), bisect, the interactive hooks with real Kane, re-runs of inconclusive tests and balance metering are built and unit-tested, not run live yet.
- **Stable criterion ids across a re-design that changes the design.** Live, a forced re-design of an unchanged use case kept every id, and an evolve kept the criteria's ids while it replaced every test id; Holdback refuses an evolve that drops a criterion of the use case.
- **An evolve that keeps the old tests.** Kane's `maintain evolve` retires every test of the use case; Holdback runs only the new set, and asks Kane once more for criteria left without a test.
- **Other platforms.** Holdback has run live on Windows only.
- **An npm package.** Install from source.
- **Results beyond one spec.** The exam measures one spec, `examples/pantry-spec/PRD.md`.
- **Anything marked pending.** It is not claimed until the file behind it exists.
